## 1. Hypotheses Beyond the Confirmed Manager Baseline

The confirmed Manager baseline is: oversee multiple auditors, monitor exposure levels, respond to SOS alerts. The three hypotheses below go beyond that baseline. Each is a team judgment call, not a request for client sign-off — the reasoning behind each is spelled out so it can be defended with confidence if asked.

**Hypothesis 1 — A plain SOS email is not enough to guarantee a fast response.**
The confirmed mechanism for an over-exposure incident is a simple manager email. We're building in an in-app urgent-state indicator (banner or badge) alongside the email, because a manager juggling around ten auditors could plausibly miss or delay-open an SOS email exactly when speed matters most against the client's own "wellbeing always wins" ruling. Reasoning to defend if asked: the confirmed mechanism sets a floor, not a ceiling, and closing the gap between "notification sent" and "manager actually saw it in time" serves the same priority the client already set.

**Hypothesis 2 — The oversight dashboard needs a proactive "approaching limit" state, not just a final exposure number.**
With per-auditor exposure limits now configurable, a dashboard that only shows current/final exposure per auditor forces the manager to manually scan roughly ten rows to catch a limit about to be crossed. We're designing a distinct "approaching limit" visual state, separate from "at limit" and "under limit," to align the dashboard with the client's own proactive-wellbeing framing rather than a passive audit log. Reasoning to defend if asked: the client's stated priority is preventing harm, not just recording it after the fact, so the dashboard should support noticing a problem before it happens.

**Hypothesis 3 — Reassigning a declined case needs more structure than free-text auditor comments.**
The confirmed decline workflow has the manager deciding whether to reassign based on the auditor's comments, the SLA/exposure limit, and the AI's output, without necessarily viewing the source content. We're proposing a structured decline-reason field alongside free text, so the manager can decide quickly and consistently in the common case. This sits behind an already lower-build-priority feature, so it's a Week 1/2 design intention to build toward, not an immediate ask. The Auditor Assumptions Note now adds a second decline entry point — a queue-level skip, triggered from the visible severity tag before a case is even opened, alongside the existing post-open decline at the warning gate — so the structured reason field should distinguish the two ("skipped based on visible severity, not opened" vs. a reason given after opening); they represent different auditor experiences and are useful to tell apart in later pattern-review, even though both route to the Manager identically and neither carries any penalty.

**Hypothesis 4 — A wellbeing check-in needs a structurally distinct manager-side surface, not the SOS alert restyled.**
The Auditor Assumptions Note (Stages 4 and 8) confirms two team-designed points at which an auditor can raise a wellbeing check-in that is explicitly kept "distinct from SOS" and free of "urgent/alarm framing." Nothing in this note or any Manager-side source currently says how that check-in should land on the manager's screen; left undesigned, the default risk is a re-skinned version of the same SOS banner/badge (Hypothesis 1), which would erase the distinction the auditor-side design was built to protect. We're placing the check-in inside the auditor's normal case/record view — the same surface already used for case/exposure context in Stages 3–4 of the SOS flow below — rather than the SOS urgent-alerts surface, with no acknowledgment workflow attached and no accompanying email. Reasoning to defend if asked: Reese's persona establishes the manager's default working register as calm and glanceable, "punctuated only occasionally" by the urgent register Jordan's SOS persona lives in more often, and Marielle Lee (Q1, Q4) both warn against visually loud or repeated protective signals — manufacturing urgency for a routine, optional, low-severity signal would tip protective into surveillance-feeling, the exact failure mode Marielle Lee flagged, and would undo the distinction the auditor-side design already drew.

**Hypothesis 5 — When a Manager does need to see raw footage, they get the same protections as an Auditor, not fewer.**
The confirmed and Hypothesis 3 reassignment workflow keeps the Manager off raw content by default. For the genuinely exceptional case where structured signals (AI output, Auditor comments, exposure/SLA data) aren't enough to decide, the Manager needs a path to view the source directly — but that path shouldn't be an unprotected side door. Adopted 27 Aug 2026: the Manager passes through the exact same content-warning modal, AI summary, and blur/grayscale controls an Auditor would, before any raw content is shown. Reasoning to defend if asked: Safe Work Australia's Managing Psychosocial Hazards at Work Code of Practice scopes traumatic-material exposure protections to *any worker* exposed to it, not to a named job title — so there's no principled reason a Manager stepping into raw-footage review, even occasionally, should get weaker protections than the Auditor whose job is built around them.

Sourced from our Week 1 manager research notes and the three dedicated Manager persona variants in Part A (Jordan, Reese, Sam), each of which maps to one of these hypotheses as its dominant lens. Hypothesis 4 draws additionally on the companion `auditor-assumptions-note-sprint1-week2.md` (Stages 4 and 8) and Marielle Lee's own interview (Q1, Q4, Q6). Hypothesis 5 draws on Safe Work Australia's Managing Psychosocial Hazards at Work Code of Practice, the same source already grounding the Auditor Assumptions Note's wellbeing protections.

### 1a. Exposure Threshold Calibration — What "Approaching" Actually Means (Extends Hypothesis 2)

**Proposed 27 Aug 2026 — real source, still needs sign-off.** Hypothesis 2 above establishes *that* a distinct "approaching limit" state should exist; it never set the actual number that switches the dashboard row into that state. Left unset, this isn't a neutral gap — a default that's too close to 100% (e.g., 90%) gives the Manager almost no runway to act before the Auditor is capped anyway, quietly turning "approaching" into "already basically at limit" and defeating the whole proactive point of Hypothesis 2; a default that's too far from 100% (e.g., 25%) would flag most of the team as "approaching" for most of a normal day, producing exactly the same low-signal noise the team already rejected elsewhere (no aggregated decline counts, no per-check-in tally — see the MR-CR-04/AR-DF-03 reasoning). The number itself is the design decision, not a rounding detail.

**Proposed threshold: 50% of the Auditor's applicable exposure cap consumed** — at the default 120-minute testing cap (CV-03), that's 60 minutes. Below 50%: shown as comfortably under. 50%–99%: "approaching." 100%+: "at limit," per AR-WB-03.

**Sourced from:** OSHA's occupational exposure limit framework — specifically the **Action Level** concept used across its Permissible Exposure Limit (PEL) standards. An Action Level is a lower, earlier threshold than the legal exposure limit itself, set specifically to trigger additional monitoring and protective action *before* a worker reaches the full limit, not at the limit itself. Across OSHA's PEL standards, 50% of the full PEL is the single most common calibration for the Action Level — e.g. the Respirable Crystalline Silica standard (29 CFR 1910.1053) sets its Action Level at 25 µg/m³ against a 50 µg/m³ PEL, exactly half. It isn't a universal fixed rule, though: the Lead standard (29 CFR 1910.1025) sets its Action Level at 30 µg/m³ against a 50 µg/m³ PEL — 60%, not 50% — so the exact fraction is calibrated per hazard by the regulator, not derived from one formula. 50% is presented here as the dominant, most-defensible default calibration, not the only possible one.

**Why this specific number gives real runway, not a token buffer.** At 50% consumed on the 120-minute cap, a Manager sees the amber state with a full 60 minutes of headroom still remaining for that Auditor — enough to cover, for example, an entire S3 case cooldown (15 minutes, mandatory) plus several more S1/S2 cases, or a full S4 cooldown (30 minutes minimum) with room to spare, before that Auditor would actually need to be pulled from new assignments. That's the difference between "noticed with time to actually do something" (reprioritise lower-severity cases toward this Auditor, or simply keep an eye on them) and "noticed right as it stops mattering." A narrower buffer collapses that gap; a wider one drowns the signal in noise.

**Honest limits of the analogy — flag before presenting to Naresh.** OSHA's Action Levels govern *chemical and physical* exposure (airborne contaminant concentration), not psychological exposure to distressing content — there is no direct clinical equivalence being claimed here, and no source suggests one exists. What transfers is the *structural* idea: regulators facing an analogous problem (how early should a warning threshold sit below a hard exposure limit to still be useful) converged on "roughly half" as the default answer, which is a real, checkable data point to reason from rather than a number invented for this dashboard. That's the basis for the proposal — an analogy to real regulatory design practice, not a claim that OSHA has studied content moderators.

**Status: proposed, not yet client- or BA-confirmed.** Same category as the rest of this note's hypotheses — a team judgment call, made with a real citation behind it, ready to defend to Naresh, not something awaiting his ruling first. Corresponding proposed requirement: MR-OV-07 (see the requirements doc).

### 1b. Unacknowledged SOS — Should the System Nudge Again? (Extends Hypothesis 1 / Stage 2)

**Proposed 27 Aug 2026 — mechanism sourced, exact timing genuinely open.** Hypothesis 1 closed the gap between "an SOS email was sent" and "the Manager is likely to see it fast" by adding an in-app urgent banner alongside the confirmed email. What Hypothesis 1 doesn't cover: what happens if the Manager still doesn't acknowledge it — in a meeting, phone away, genuinely didn't see the banner. Per the client's own unambiguous ruling that wellbeing always wins, no exceptions (CV-04), and Research Note 1's own framing (a manager juggling ~10 auditors "could plausibly miss or delay-open" a plain notification exactly when speed matters most), a notification that can silently go unseen with no follow-up is the single worst failure mode this design can have — someone who was just harmed by the system's own failure gets no human response at all.

**Proposed mechanism:** if an SOS alert isn't acknowledged (via the existing MR-SOS-04 acknowledge action) within a set window, the system sends **exactly one** automatic reminder — the in-app banner escalates its visual state (e.g. static becomes pulsing/repeated) and a second email goes out — rather than looping indefinitely, and rather than staying silent until someone happens to notice.

**Sourced from:** two converging bodies of real practice for exactly this kind of problem (an unacknowledged safety-relevant alert). First, clinical alarm-management and patient-safety literature on secondary notification systems — used in hospitals so that an alarm a primary clinician hasn't acknowledged automatically escalates to a secondary responder or channel rather than sitting unactioned (see e.g. peer-reviewed work on secondary device notification and alarm-escalation systems in clinical monitoring). Second, standard practice in safety-critical incident-response/on-call systems generally — escalation-policy tooling (e.g. PagerDuty) deliberately separates "initial notify," "unacknowledged re-trigger," and "escalate further" into distinct steps, precisely because a single fire-and-forget alert is known to fail silently under real-world attention load. Both are cited honestly as literature from *different* risk domains (physiological monitoring; software operations) — used here for the general design principle (unacknowledged safety alerts should re-notify, not sit silent), not as a source for this platform's specific timing.

**Deliberately not proposed:** escalating to a second/backup Manager if the first reminder also goes unacknowledged. No such role exists anywhere in the confirmed org model — this platform's structure, per the kickoff notes and both Manager persona research documents, is one Manager overseeing roughly ten Auditors directly, with no documented deputy or backup tier. Inventing one here would be adding organisational structure nobody has asked for, which is a staffing/org decision for the client or PM, not something a UX proposal should quietly assume into existence.

**On the exact interval — genuinely open, no number invented.** Neither of the two source domains above transfers a specific minute figure cleanly: the clinical literature's escalation windows are calibrated for physiological emergencies (often very short), and the incident-response convention's windows are calibrated for software-operations severity (often longer) — neither risk profile matches "a person who was just unexpectedly exposed to traumatic content and needs a human check-in soon." Rather than average two unrelated numbers into something that only sounds reasoned, this stays an open, Manager-configurable setting — the same pattern already used for AR-WB-02's exposure cap, which is a client-set default the Manager can adjust per Auditor. **Status: mechanism proposed, interval genuinely open** — corresponding proposed requirement MR-SOS-07 (see the requirements doc) covers the mechanism only.

### 2a. Manager's Receiving End of an Auditor's Wellbeing Check-in

This is a separate, lower-key flow from the SOS table above — deliberately not a row added to it. The outer shape is grounded in the confirmed auditor-side design: an auditor can raise a check-in either mid-Review (Stage 4) or during a post-high-severity cooldown (Stage 8) of the companion auditor-assumptions-note, and it must read as distinct from SOS on arrival at the manager's screen too, not just at the point it's raised.

| Stage | Manager action / thought | Status | Design note |
|---|---|---|---|
| 1. Check-in requested by auditor | Auditor-side event, not a manager action | Confirmed (per `auditor-assumptions-note-sprint1-week2.md`, Stages 4 & 8) | The auditor-side prompt (Stage 8) also carries a second, separate optional flag, "I'd like a break," distinct from the general talk-to-manager response — see that note for the exact wording |
| 2. Pushing a manager alert for every check-in was weighed against the cost of managing that across roughly ten auditors, and notification fatigue outweighs the benefit for routine check-ins. | 3. | 4. Marielle Lee's own sketch of the manager's response here ("ok, I see, take them to talk") is underdeveloped once applied to an actual screen, so this is refined further: the resolution isn't a menu of structured options (offer a break / reassign to lower severity / log and move on) — that menu reintroduces exactly the case-by-case manager workload this design avoids for routine check-ins, and "reassign to lower severity" specifically depends on assignment-weighting logic that's an open Dev/BA question (see the companion auditor note's Stage 1 flag), not something a manager screen should improvise per case. What the screen gives instead is the one concrete, low-friction action the auditor can actually ask for: approve or acknowledge a flagged break request. Anything beyond that stays a conversation, not a workflow |
| 5. Manager logs the outcome | Manager records that the check-in happened and how it was resolved | Team-designed (default, not client-confirmed) | Extends the same audit-trail logic already applied to SOS outcomes (SOS Stage 6) — logged for later pattern-review, not performance tracking. Kept deliberately unaggregated and out of any per-auditor scrutiny view, per the same no-aggregate-decline-count principle already proposed — a logged check-in should never become a visible "N check-ins this week" tally next to an auditor's name |

**S4 (critical-severity) cases are the one exception to "optional."** Per the Auditor Assumptions Note's Cooldown Severity Model, an S4 case's cooldown automatically includes a mandatory manager/support check-in, plus the auditor's option to stop or reassign the remaining shift — this isn't the auditor-initiated, optional flow described above, it's a heavier, severity-triggered escalation layer that sits alongside it. The manager-side handling is the same surface (auditor's normal case/record view, not the SOS alerts surface) and the same low-key register, but the manager follow-up itself is required, not conditional on the auditor asking for it. **Consistency check (27 Aug 2026):** this escalation trigger depends only on a case being tagged S4, not on how S4 was computed — so the Auditor Assumptions Note's severity-mechanism scope correction (simple rule-based CVI-range + tag mapping now replaces the six-factor formula as the baseline computation) doesn't change anything here. S4 is still S4; only the working behind the tag changed.

**"Stop" and "reassign" are two different actions, split deliberately.** Stopping is the Auditor's own call — no Manager approval needed, consistent with wellbeing outranking speed (CV-04). Reassigning the remaining workload is a team/queue decision that only the Manager has visibility to make, so it's handled through the mandatory check-in above rather than as a separate self-serve option.

**On how quickly the Manager needs to respond:** the S4 check-in gets the same distinct, low-key marker as a flagged break request (Stage 2 above) — not a push notification, not an email, and not a monitored deadline. "Within the 30-minute cooldown window" is useful as our own internal reasoning for how soon this should ideally be handled, since it reuses the cooldown length rather than inventing a separate SLA figure — but it is deliberately not built into the system as an enforced response time with an escalation timer attached. Doing that would require the Manager to actively monitor the dashboard in real time, which is the same "chronically online" pressure this whole flow is designed to avoid. In practice, an S4 flag is simply the highest-priority item in the Manager's normal queue, actioned the next time they check in, not something that pages them.

No email accompanies this flow: CV-08 and MR-SOS-02 are scoped specifically to unexpected harmful exposure (the SOS path), not to a routine check-in, and adding email here would work against the same "don't make it loud" principle (Marielle Lee Q4) driving the rest of this flow's design.

**Check-in-frequency escalation threshold — proposed 27 Aug 2026, distinct from S4's severity-based escalation above (which is resolved).** A single routine check-in (no break flagged) correctly requires no Manager action, per Stage 4 above — treating every optional, low-severity signal as needing formal response would recreate the exact "info overload with no purpose" problem the team already rejected for aggregated decline counts (see the MR-CR-04/AR-DF-03 reasoning) and for constant visible protective signals generally (Marielle Lee Q1, Q4). But a *pattern* of routine check-ins from the same Auditor is a genuinely different signal than any single one of them — it's precisely the kind of early warning this platform's wellbeing-first design exists to catch, and as currently designed, nothing anywhere notices a pattern; the system only ever sees one check-in at a time.

Proposed threshold: **three or more routine check-ins (no break flagged) from the same Auditor within a defined rolling period** move that Auditor from "logged only" to a distinct, low-key "pattern flagged" marker in the Manager's normal case/record view — reusing the exact same low-key surface already used for the break-request flag (Stage 2 above, MR-WB-02), not an alarm and not an email, consistent with the same "don't make it loud" principle (Marielle Lee Q4) already governing this entire section. This is deliberately *not* a running, visible tally next to the Auditor's name (e.g. no "4 check-ins this month") — it's a private, Manager-only prompt to have a conversation, for the same reason the decline-reassurance reasoning already rejected a visible decline counter: a tally reads as a performance record; a quiet nudge to check in doesn't.

**Sourced from:** established practice in safety leading-indicator/near-miss investigation management — a repeated pattern of the same non-severe signal, from the same source, within a short period, is treated as itself the trigger for review, independent of whether any single instance was serious (a common working convention is three or more of the same near-miss signal in a short period warranting investigation, on the reasoning that repetition, not severity, is what indicates a systemic issue rather than a one-off). This is cited honestly as established safety-management practice, not a peer-reviewed clinical study — the same tone already used for this section's own S4 response-time reasoning above, which similarly reused an existing figure (the cooldown length) as *internal* reasoning rather than an enforced, independently-derived standard.

**On the exact window — genuinely open, no number invented.** The count (three) is the grounded part of this proposal; the period it applies over — a week, a rolling fortnight, a review block — has no equivalent source anywhere in the material reviewed for this project, and is left as an open implementation detail rather than an invented one. Per Hyuna's 27 Aug 2026 feedback delegating the remaining open items to Jana's own research, the exact window stays Jana/BA-owned, alongside final sign-off on the threshold count itself — this is a sourced UX proposal, not a client ruling or an item the team can self-close. ## 3. Manager's Likely Background/Context (Brief Note)

The Manager sits one level above the Auditor day-to-day: typically promoted from several years as a senior auditor rather than hired externally, overseeing roughly ten auditors within the same safety/trust function. They don't do frontline content review as their main job — their role is oversight, tracking exposure and workload, responding to wellbeing escalations, and deciding on declined-case reassignment. Per our Week 1 manager research and the three dedicated Manager persona variants in Part A, this isn't one fixed working style but three genuinely different postures: reactive, centred on responding fast to SOS escalations and declined-case interruptions (Jordan); proactive, centred on watching exposure and workload before problems occur (Reese); and reassignment-and-fairness, centred on deciding declined cases at volume without viewing the source content (Sam). No real managers have been interviewed — the client deliberately left this role's view undesigned (per the kickoff notes: "Naresh explicitly wants the team to design this themselves using their own imagination — this is a deliberate gap, not an oversight"), so this background, like the rest of the Manager persona set, is a team-defined working hypothesis rather than a confirmed profile.
