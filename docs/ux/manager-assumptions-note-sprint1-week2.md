## 1. Hypotheses Beyond the Confirmed Manager Baseline

The confirmed Manager baseline is: oversee multiple auditors, monitor exposure levels, respond to SOS alerts. The three hypotheses below go beyond that baseline. Each is a team judgment call, not a request for client sign-off — the reasoning behind each is spelled out so it can be defended with confidence if asked.

**Hypothesis 1 — A plain SOS email is not enough to guarantee a fast response.**
The confirmed mechanism for an over-exposure incident is a simple manager email. We're building in an in-app urgent-state indicator (banner or badge) alongside the email, because a manager juggling around ten auditors could plausibly miss or delay-open an SOS email exactly when speed matters most against the client's own "wellbeing always wins" ruling. Reasoning to defend if asked: the confirmed mechanism sets a floor, not a ceiling, and closing the gap between "notification sent" and "manager actually saw it in time" serves the same priority the client already set.

**Hypothesis 2 — The oversight dashboard needs a proactive "approaching limit" state, not just a final exposure number.**
With per-auditor exposure limits now configurable, a dashboard that only shows current/final exposure per auditor forces the manager to manually scan roughly ten rows to catch a limit about to be crossed. We're designing a distinct "approaching limit" visual state, separate from "at limit" and "under limit," to align the dashboard with the client's own proactive-wellbeing framing rather than a passive audit log. Reasoning to defend if asked: the client's stated priority is preventing harm, not just recording it after the fact, so the dashboard should support noticing a problem before it happens.

**Hypothesis 3 — Reassigning a declined case needs more structure than free-text auditor comments.**
The confirmed decline workflow has the manager deciding whether to reassign based on the auditor's comments, the SLA/exposure limit, and the AI's output, without necessarily viewing the source content. We're proposing a structured decline-reason field alongside free text, so the manager can decide quickly and consistently in the common case. This sits behind an already lower-build-priority feature, so it's a Week 1/2 design intention to build toward, not an immediate ask. The Auditor Assumptions Note now adds a second decline entry point — a queue-level skip, triggered from the visible severity tag before a case is even opened, alongside the existing post-open decline at the warning gate — so the structured reason field should distinguish the two ("skipped based on visible severity, not opened" vs. a reason given after opening); they represent different auditor experiences and are useful to tell apart in later pattern-review, even though both route to the Manager identically and neither carries any penalty.

**Hypothesis 4 — A wellbeing check-in needs a structurally distinct manager-side surface, not the SOS alert restyled.**
The Auditor Assumptions Note (Stages 4 and 8) confirms two team-designed points at which an auditor can raise a wellbeing check-in that is explicitly kept "distinct from SOS" and free of "urgent/alarm framing." Nothing in this note or any Manager-side source currently says how that check-in should land on the manager's screen; left undesigned, the default risk is a re-skinned version of the same SOS banner/badge (Hypothesis 1), which would erase the distinction the auditor-side design was built to protect. We're placing the check-in inside the auditor's normal case/record view — the same surface already used for case/exposure context in Stages 3–4 of the SOS flow below — rather than the SOS urgent-alerts surface, with no acknowledgment workflow attached and no accompanying email. Reasoning to defend if asked: Reese's persona establishes the manager's default working register as calm and glanceable, "punctuated only occasionally" by the urgent register Jordan's SOS persona lives in more often, and Marielle Lee (Q1, Q4) both warn against visually loud or repeated protective signals — manufacturing urgency for a routine, optional, low-severity signal would tip protective into surveillance-feeling, the exact failure mode Marielle Lee flagged, and would undo the distinction the auditor-side design already drew.

**Hypothesis 5 — When a Manager does need to see raw footage, they get the same protections as an Auditor, not fewer.**
The confirmed and Hypothesis 3 reassignment workflow keeps the Manager off raw content by default. For the genuinely exceptional case where structured signals (AI output, Auditor comments, exposure/SLA data) aren't enough to decide, the Manager needs a path to view the source directly — but that path shouldn't be an unprotected side door. Adopted 27 Aug 2026: the Manager passes through the exact same content-warning modal, AI summary, and blur/grayscale controls an Auditor would, before any raw content is shown. Reasoning to defend if asked: Safe Work Australia's Managing Psychosocial Hazards at Work Code of Practice scopes traumatic-material exposure protections to *any worker* exposed to it, not to a named job title — so there's no principled reason a Manager stepping into raw-footage review, even occasionally, should get weaker protections than the Auditor whose job is built around them.

**Gap found in end-to-end review, 27 Aug 2026 (proposed by UX, needs team sign-off) — Hypothesis 5 gives the Manager the same viewing *protections* as an Auditor, but says nothing about the same viewing *tracking*.** The Auditor side of this platform doesn't just gate raw content behind a warning — it counts every second of it against a daily exposure cap, exactly because that's what the Safe Work Australia source treats as the actual protective mechanism, not just the warning gate on its own. Hypothesis 5's own reasoning (protections are worker-scoped, not job-title-scoped) applies just as much to *exposure tracking* as it does to the warning modal and blur controls — there's no principled reason to stop halfway through adopting the same source's logic. **Proposed fix:** when a Manager views raw content under Hypothesis 5, that viewing time is logged the same way an Auditor's active-playback time is logged (AR-WB-01/02's counting rule — active playback counts regardless of blur/grayscale/mute, replays count again). **This does not mean giving Managers a hard 120-minute cap the way Auditors have one** — a Manager's exceptional, occasional raw-footage review isn't the same daily workload pattern a cap was designed to prevent, and inventing a Manager exposure cap with no basis would be exactly the kind of unsourced number this project avoids elsewhere. The proposal is scoped to **visibility, not a limit**: the Manager's own logged raw-footage viewing time appears somewhere they (or, if the team later wants it, their own oversight) can see it — so it's tracked and auditable rather than invisible, without inventing a threshold nobody asked for. **Needs your sign-off** — this is a genuine gap, not a client ruling, and the team should decide whether tracking-only is sufficient or whether a cap is wanted after all.

Sourced from our Week 1 manager research notes and the three dedicated Manager persona variants in Part A (Jordan, Reese, Sam), each of which maps to one of these hypotheses as its dominant lens. Hypothesis 4 draws additionally on the companion `auditor-assumptions-note-sprint1-week2.md` (Stages 4 and 8) and Marielle Lee's own interview (Q1, Q4, Q6). Hypothesis 5 draws on Safe Work Australia's Managing Psychosocial Hazards at Work Code of Practice, the same source already grounding the Auditor Assumptions Note's wellbeing protections.

### 1a. Exposure Threshold Calibration — What "Approaching" Actually Means (Extends Hypothesis 2)

**Adopted 27 Aug 2026 — team-defined operational rule.** Hypothesis 2 above establishes *that* a distinct "approaching limit" state should exist; it never set the actual number that switches the dashboard row into that state. Left unset, this isn't a neutral gap — a default that's too close to 100% (e.g., 90%) gives the Manager almost no runway to act before the Auditor is capped anyway, quietly turning "approaching" into "already basically at limit" and defeating the whole proactive point of Hypothesis 2; a default that's too far from 100% (e.g., 25%) would flag most of the team as "approaching" for most of a normal day, producing exactly the same low-signal noise the team already rejected elsewhere (no aggregated decline counts, no per-check-in tally — see the MR-CR-04/AR-DF-03 reasoning). The number itself is the design decision, not a rounding detail.

**Adopted threshold: 75% of the Auditor's applicable exposure cap consumed** — at the default 120-minute testing cap (CV-03), that's 90 minutes. Below 75%: shown as comfortably under. 75%–99%: "approaching." 100%+: "at limit," per AR-WB-03.

**Basis for the number — team-defined, not an external standard.** An earlier version of this note reasoned from OSHA's occupational "Action Level" convention (a lower warning threshold set below a hard chemical-exposure limit, commonly calibrated at 50% of the limit) as a structural analogy. On review, the team judged that comparison too weak to carry a specific percentage here — chemical exposure limits and psychological exposure to distressing content aren't close enough in kind for a borrowed number to do real work, even as an analogy. 75% is instead the team's own operational call, made with the same confidence as this note's other hypotheses.

**Why 75% gives real runway, not a token buffer.** At 75% consumed on the 120-minute cap, a Manager sees the amber state with 30 minutes of headroom still remaining for that Auditor — enough to cover a full S3 cooldown (15 minutes, mandatory) with room left over, though tighter than a lower threshold would allow for an S4 cooldown (30 minutes minimum) without immediately pushing the Auditor to the cap. That tradeoff is deliberate: 75% sits closer to the cap than a wider buffer would, which keeps the "approaching" state meaningful and rare rather than something most of the team sees most days — the team weighed a narrower, more urgent-feeling signal against a longer runway, and chose to keep the signal meaningful.

**Status: adopted as the team's working design intention, not yet client-confirmed.** Same category as the rest of this note's hypotheses — a team judgment call, ready to defend to Naresh if asked, not something awaiting his ruling first. Corresponding requirement: MR-OV-07 (see the requirements doc).

**CONFIRMED — 28 Aug 2026, per Jana's finalised baseline.** This threshold survives into Jana's finalised requirements doc, folded into her MR-OV-05 (rather than kept as a separate MR-OV-07 ID): *"Approaching Limit begins at 75% of the applicable exposure cap (90 minutes when the default 120-minute testing cap applies); At Limit begins at 100%,"* explicitly labelled a team-defined operational threshold. Same number, same reasoning — just a different ID in her canonical doc. No reconciliation needed.

### 1b. Unacknowledged SOS — Should the System Nudge Again? (Extends Hypothesis 1 / Stage 2)

**Adopted 27 Aug 2026 — mechanism sourced, timing team-defined.** Hypothesis 1 closed the gap between "an SOS email was sent" and "the Manager is likely to see it fast" by adding an in-app urgent banner alongside the confirmed email. What Hypothesis 1 doesn't cover: what happens if the Manager still doesn't acknowledge it — in a meeting, phone away, genuinely didn't see the banner. Per the client's own unambiguous ruling that wellbeing always wins, no exceptions (CV-04), and Research Note 1's own framing (a manager juggling ~10 auditors "could plausibly miss or delay-open" a plain notification exactly when speed matters most), a notification that can silently go unseen with no follow-up is the single worst failure mode this design can have — someone who was just harmed by the system's own failure gets no human response at all.

**Adopted mechanism:** if an SOS alert isn't acknowledged (via the existing MR-SOS-04 acknowledge action) within **3 minutes**, the system sends **exactly one** automatic reminder — the in-app banner escalates its visual state (e.g. static becomes pulsing/repeated) and a second email goes out — rather than looping indefinitely, and rather than staying silent until someone happens to notice. SOS stays a distinct, urgent action throughout — separate from the routine wellbeing check-in and break-request flows in Section 2a below, which deliberately stay low-key.

**Sourced from (mechanism only):** two converging bodies of real practice for exactly this kind of problem (an unacknowledged safety-relevant alert). First, clinical alarm-management and patient-safety literature on secondary notification systems — used in hospitals so that an alarm a primary clinician hasn't acknowledged automatically escalates to a secondary responder or channel rather than sitting unactioned (see e.g. peer-reviewed work on secondary device notification and alarm-escalation systems in clinical monitoring). Second, standard practice in safety-critical incident-response/on-call systems generally — escalation-policy tooling (e.g. PagerDuty) deliberately separates "initial notify," "unacknowledged re-trigger," and "escalate further" into distinct steps, precisely because a single fire-and-forget alert is known to fail silently under real-world attention load. Both are cited honestly as literature from *different* risk domains (physiological monitoring; software operations) — used here for the general design principle (unacknowledged safety alerts should re-notify, not sit silent), not as a source for this platform's specific timing.

**The 3-minute figure itself is a team-defined operational rule, not a clinically-derived number.** Neither source domain above transfers a specific minute figure cleanly: the clinical literature's escalation windows are calibrated for physiological emergencies, and the incident-response convention's windows are calibrated for software-operations severity — neither risk profile matches "a person who was just unexpectedly exposed to traumatic content and needs a human check-in soon." Rather than dress up a borrowed number as sourced, the team set 3 minutes directly: short enough that a genuinely urgent alert doesn't sit unescalated for long, long enough that a Manager mid-task isn't immediately double-notified for something they were already about to acknowledge.

**Deliberately not adopted:** escalating to a second/backup Manager if the reminder also goes unacknowledged. No such role exists anywhere in the confirmed org model — this platform's structure, per the kickoff notes and both Manager persona research documents, is one Manager overseeing roughly ten Auditors directly, with no documented deputy or backup tier. Inventing one here would be adding organisational structure nobody has asked for, which is a staffing/org decision for the client or PM, not something a UX proposal should quietly assume into existence. **This stays deliberately open, not designed around silently:** if the team ever hits a real situation where a single Manager with no backup becomes an actual operational problem (e.g. an unacknowledged SOS with no one else to route to), that's a question for Hyuna to raise with Naresh directly — an org/staffing decision, not one this note should pre-empt by inventing a deputy role nobody has asked for.

**Status: adopted as the team's working design intention** — both the mechanism (real citations) and the 3-minute figure (team-defined) are settled. Corresponding requirement: MR-SOS-07 (see the requirements doc).

**UPDATED — 28 Aug 2026, per Jana's finalised Sprint 2 BA baseline.** Jana's finalised requirements doc (`PERSONA-BA-REQ.md`) doesn't include MR-SOS-07 as a numbered Mandatory requirement; her Manager follow-up notes state directly: *"The exact visual escalation/reminder behaviour for unresolved in-app SOS alerts remains a UX/implementation detail; the confirmed baseline is Manager notification and follow-up, with email for unexpected exposure."* So this section's specific mechanism (3-minute timer, exactly one reminder, banner escalation) stays this note's working design proposal — genuinely good, sourced reasoning worth building toward — but it's a UX/implementation detail layered on top of the confirmed baseline (MR-SOS-01/02/06 equivalent: notify, follow up, email for unexpected exposure), not itself an adopted Mandatory requirement in the finalised BA doc.

### 1c. Ground-Truth Accuracy Validation — A Client-Requested Requirement With No Owner (New, Found and Proposed 27 Aug 2026)

**Gap found in end-to-end review, not raised by any earlier task.** In the Sprint 1 Q&A, Naresh directly asked how severity scoring should be validated, and answered his own question clearly: when submitting accuracy results, the team should show **manual stats — e.g. a graph — demonstrating how the AI's output performs against expected (ground-truth) outcomes for a sample set of cases.** The capstone brief's own success criteria say the same thing from the other direction: "vision classification meets an agreed accuracy threshold on the synthetic/staged validation set." Despite being an explicit, repeated client ask, this has never been written down as an actual requirement anywhere in the Normal User, Auditor, or Manager sections — it exists only as background context, owned by nobody.

**Proposed home: the Manager's oversight surface, as a distinct validation view — not mixed into live case review.** The Manager already has the platform's only broader-than-Auditor visibility (MR-OV-06), and this is fundamentally an oversight function: checking whether the AI is doing its job, not reviewing an individual case. It should **not** live inside the live case queue, since a validation/ground-truth comparison depends on a known-answer test set (the project's own synthetic/staged validation footage, per the brief), not on real public submissions, which have no independently-verified "correct" severity to compare against.

**MR-OV-08 (proposed).** *The Manager dashboard shall provide a distinct validation view, separate from live case oversight, showing the AI pipeline's severity/tag output compared against the manually-labelled ground-truth values for the project's synthetic/staged validation case set, summarised as a graph or simple accuracy statistic — satisfying the client's explicit request for demonstrated accuracy validation (client Q&A, item 9) and the capstone brief's own success criterion for the vision-classification accuracy threshold.*

**Priority — team-defined, by analogy to how this project already prioritises validation/reporting features.** This isn't part of the core live-case flow, and the project already has a working precedent for treating validation/reporting-style features as lower build priority than the main end-to-end flow (the declined-case workflow, AR-DF-05/MR-CR-07/CV-09). Proposed the same way: build toward this once the main Auditor/Manager review flow works end to end, not before. **Needs your sign-off** — this is a genuinely new finding, not a client ruling on exactly how to build it, only on the fact that something like it is expected.

### 1d. What Counts as "Agreed Accuracy" — Validation Metric & Threshold (Extends MR-OV-08) — proposed 27 Aug 2026, gap found in end-to-end review

**The gap.** MR-OV-08 builds the *view* — a dashboard comparing the AI's severity/tag output against manually-labelled ground truth on the synthetic/staged validation set. It never says what number, on what metric, counts as passing. The capstone brief's own success criterion ("vision classification meets an agreed accuracy threshold") names this explicitly as something the team needs to agree on, not just display.

**First correction: "accuracy" is very likely the wrong headline metric, not just an unset number.** Real content-moderation/ML validation practice treats raw accuracy as actively misleading for this kind of task: most submitted content will not be violative, so a classifier could score a high "accuracy" percentage just by predicting "not harmful" most of the time, while still missing the harmful content that actually matters. Wei, Zufall & Jia's peer-reviewed work on operationalising content-moderation "accuracy" (AIES 2024) states this directly: "the literal accuracy... is not suitable for problems with large class imbalance," recommending precision and recall be reported separately instead, since both remain informative under imbalance where raw accuracy misleads. This is real, on-point, peer-reviewed research about content moderation specifically, not a generic ML citation borrowed by analogy — and per AR-AI-13 (Auditor Assumptions Note), this platform has already adopted a recall-priority stance (favour catching true harmful content over avoiding over-flagging, per CV-04). That means **recall should be MR-OV-08's headline reported number**, not a single blended accuracy percentage, with precision shown alongside for context rather than as the primary pass/fail bar.

**Second correction: no external source sets an exact transferable number for this project's own bar — and pretending otherwise would be the kind of invented precision this project avoids elsewhere.** No published source hands over a percentage that transfers cleanly to this platform's own categories and validation set — trying to borrow one from an unrelated content-moderation task (e.g. text-based classifiers, or benchmarks scored on different category definitions) would be exactly the kind of unsourced-number-dressed-as-sourced this project avoids elsewhere. What real practice does support is the *logic* of where the bar should sit: trust & safety industry practice sets category-specific recall floors, with CSAM-adjacent/child-safety categories getting the strictest floor because a missed detection is the severe failure mode — the same recall-priority logic already adopted at AR-AI-13. Son et al.'s peer-reviewed work on content-moderation threshold optimisation (WSDM 2023) supports deriving the exact number empirically from the real validation set via threshold optimisation once it exists, rather than guessing a permanent figure now.

**Proposed threshold — team-defined operational rule, informed by the sourced logic above but not derived from any single external number:** **recall ≥ 90%, with precision also reported (no separate hard minimum on it)**, measured against the project's own synthetic/staged validation set once Dev's rules engine exists to produce a real score (Phase 3, Weeks 6–8). Recall is set as the only hard bar, consistent with AR-AI-13's recall-priority ruling — precision is reported for visibility and to catch a pipeline that's simply flagging everything (which would trivially max out recall while being useless), not because it independently gates a pass/fail decision.

**What would tighten this later:** exactly the same caveat already stated for the CVI-range cutoffs — re-calibrate against real observed performance once the actual pipeline exists and has been run against the validation set, via the empirical threshold-optimisation approach Son et al. describe, rather than treating this starting number as permanent.

**MR-OV-09 (proposed, not adopted this pass).** *MR-OV-08's validation view shall report recall and precision separately (not a single blended accuracy percentage) computed against the project's synthetic/staged validation set, and the pipeline shall be considered to meet the capstone brief's "agreed accuracy threshold" success criterion at a minimum recall of 90%, consistent with the recall-priority rule adopted in AR-AI-13.*

**Sourced from:** Wei, Zufall & Jia, "Operationalizing content moderation 'accuracy' in the Digital Services Act" (AIES 2024, arxiv.org/abs/2305.09601) — the metric-choice argument (precision/recall over blended accuracy), real and peer-reviewed; Son et al., "Reliable Decision from Multiple Subtasks through Threshold Optimization: Content Moderation in the Wild" (WSDM 2023) — precedent for deriving thresholds empirically from a validation set rather than fixing one permanently; and the same trust & safety category-floor practice already cited at AR-AI-13 (Auditor Assumptions Note) for the recall-priority logic. The 90% figure itself is a team-defined starting point, not something any of these sources hands over directly.

**Status: DEFERRED, 27 Aug 2026 (Jana, BA scope decision).** The metric choice (recall as headline, not raw accuracy) is well-grounded in real practice, but a proposed number shouldn't become a formal requirement just because someone proposed it — adding this to the Sprint 2 baseline went beyond this task's actual scope. Kept as reasoning on record, revisitable once Dev's rules engine and real validation-set results exist (Phase 3).

**CONFIRMED — 28 Aug 2026, per Jana's finalised baseline.** Jana's finalised requirements doc adds **CV-10** (client-confirmed, Final): *"When reporting AI/model performance, the project shall provide manually labelled ground-truth statistics for a sample set and present the comparison graphically."* Her notes column is explicit that this is *"a validation/reporting output, not a new Manager-dashboard feature or a 90% recall threshold"* — directly naming and declining this section's specific MR-OV-09 proposal. CV-10 covers the client's actual ask (Q&A item 9: manual stats/graph against ground truth); it deliberately doesn't adopt a metric methodology (recall vs. accuracy) or a specific number. This confirms the deferral above rather than changing it — nothing further to reconcile.

Kept deliberately unaggregated and out of any per-auditor scrutiny view, per the same no-aggregate-decline-count principle already proposed — a logged check-in should never become a visible "N check-ins this week" tally next to an auditor's name |

**S4 (critical-severity) cases are the one exception to "optional."** Per the Auditor Assumptions Note's Four-Tier Business Severity Model, an S4 case's cooldown automatically includes a mandatory manager/support check-in, plus the auditor's option to stop or reassign the remaining shift — this isn't the auditor-initiated, optional flow described above, it's a heavier, severity-triggered escalation layer that sits alongside it. The manager-side handling is the same surface (auditor's normal case/record view, not the SOS alerts surface) and the same low-key register, but the manager follow-up itself is required, not conditional on the auditor asking for it. **Consistency check (27 Aug 2026, reconfirmed 27 Aug 2026 with the CVI-range cutoffs added):** this escalation trigger depends only on a case being tagged S4, not on how S4 was computed or which CVI range triggers it — so neither the Auditor Assumptions Note's severity-mechanism scope correction (simple rule-based CVI-range + tag mapping replacing the six-factor formula) nor the newly-approved CVI-range cutoffs (85–100, or floor-forced by tag) change anything here. S4 is still S4, and — worth restating given how easy this is to blur — **reaching S4 still does not trigger SOS**; this mandatory check-in is the calm, severity-triggered response, while SOS stays reserved solely for unexpected exposure. Only the working behind the S4 tag changed.

**"Stop" and "reassign" are two different actions, split deliberately.** Stopping is the Auditor's own call — no Manager approval needed, consistent with wellbeing outranking speed (CV-04). Reassigning the remaining workload is a team/queue decision that only the Manager has visibility to make, so it's handled through the mandatory check-in above rather than as a separate self-serve option.

**On how quickly the Manager needs to respond:** the S4 check-in gets the same distinct, low-key marker as a flagged break request (Stage 2 above) — not a push notification, not an email, and not a monitored deadline. "Within the 30-minute cooldown window" is useful as our own internal reasoning for how soon this should ideally be handled, since it reuses the cooldown length rather than inventing a separate SLA figure — but it is deliberately not built into the system as an enforced response time with an escalation timer attached. Doing that would require the Manager to actively monitor the dashboard in real time, which is the same "chronically online" pressure this whole flow is designed to avoid. In practice, an S4 flag is simply the highest-priority item in the Manager's normal queue, actioned the next time they check in, not something that pages them.

No email accompanies this flow: CV-08 and MR-SOS-02 are scoped specifically to unexpected harmful exposure (the SOS path), not to a routine check-in, and adding email here would work against the same "don't make it loud" principle (Marielle Lee Q4) driving the rest of this flow's design.

**Check-in-frequency escalation threshold — adopted 27 Aug 2026, distinct from S4's severity-based escalation above (which is resolved).** A single routine check-in (no break flagged) correctly requires no Manager action, per Stage 4 above — treating every optional, low-severity signal as needing formal response would recreate the exact "info overload with no purpose" problem the team already rejected for aggregated decline counts (see the MR-CR-04/AR-DF-03 reasoning) and for constant visible protective signals generally (Marielle Lee Q1, Q4). But a *pattern* of routine check-ins from the same Auditor is a genuinely different signal than any single one of them — it's precisely the kind of early warning this platform's wellbeing-first design exists to catch, and as currently designed, nothing anywhere notices a pattern; the system only ever sees one check-in at a time.

Adopted threshold: **three or more routine check-ins (no break flagged) from the same Auditor within the same working day** move that Auditor from "logged only" to a distinct, low-key "pattern flagged" marker in the Manager's normal case/record view — reusing the exact same low-key surface already used for the break-request flag (Stage 2 above, MR-WB-02), not an alarm and not an email, consistent with the same "don't make it loud" principle (Marielle Lee Q4) already governing this entire section. A same-day window was chosen deliberately over a longer rolling period: exposure is already tracked and reset on a daily cadence (AR-WB-01/02), so reusing that same natural unit keeps this threshold legible against a boundary the Auditor and Manager already both think in, rather than introducing a second, differently-scoped tracking window. This is deliberately *not* a running, visible tally next to the Auditor's name (e.g. no "4 check-ins this month") — it's a private, Manager-only prompt to have a conversation, for the same reason the decline-reassurance reasoning already rejected a visible decline counter: a tally reads as a performance record; a quiet nudge to check in doesn't.

**Sourced from (the count, not the window):** established practice in safety leading-indicator/near-miss investigation management — a repeated pattern of the same non-severe signal, from the same source, within a short period, is treated as itself the trigger for review, independent of whether any single instance was serious (a common working convention is three or more of the same near-miss signal in a short period warranting investigation, on the reasoning that repetition, not severity, is what indicates a systemic issue rather than a one-off). This is cited honestly as established safety-management practice, not a peer-reviewed clinical study. The same-day window itself is a team-defined operational choice, reasoned above from the existing daily exposure cadence rather than from this source.

**Status: adopted as the team's working design intention.** Corresponding requirement: MR-WB-05 (see the requirements doc).

## 3. Manager's Likely Background/Context (Brief Note)

The Manager sits one level above the Auditor day-to-day: typically promoted from several years as a senior auditor rather than hired externally, overseeing roughly ten auditors within the same safety/trust function. They don't do frontline content review as their main job — their role is oversight, tracking exposure and workload, responding to wellbeing escalations, and deciding on declined-case reassignment. Per our Week 1 manager research and the three dedicated Manager persona variants in Part A, this isn't one fixed working style but three genuinely different postures: reactive, centred on responding fast to SOS escalations and declined-case interruptions (Jordan); proactive, centred on watching exposure and workload before problems occur (Reese); and reassignment-and-fairness, centred on deciding declined cases at volume without viewing the source content (Sam). No real managers have been interviewed — the client deliberately left this role's view undesigned (per the kickoff notes: "Naresh explicitly wants the team to design this themselves using their own imagination — this is a deliberate gap, not an oversight"), so this background, like the rest of the Manager persona set, is a team-defined working hypothesis rather than a confirmed profile.
