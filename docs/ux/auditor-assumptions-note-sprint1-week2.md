## 1. Auditor's Core Flow — Click-Path (Mapped Before Screen Sketches)

This is the click-path the two upcoming screens (content warning, AI analysis summary) sit inside. The outer shape is client-confirmed from the kickoff demo and the sprint-review Q&A: a submitted case gets assigned to an auditor, the auditor passes through a warning gate before viewing flagged content, reviews it, and submits findings to the manager. Where the client left specifics open, this table marks the team's working design intention.

**Reading this as four flows:** the 9 stages below collapse into four flows that serve as a shared mental model for the wider team. This is a plain-language index into the same stages, not a replacement for them — use it for a quick shared picture, and the table below for the actual design detail and citations.
1. **Normal Review** — Stages 1–5: assigned → queue → consent gate → review → submission.
2. **High-Severity Cooldown** — Stages 6–9: submission triggers cooldown → cooldown screen → wellbeing check-in → return to queue.
3. **Decline** (branches off Stage 3) — routes straight to the manager; no SOS, no push alert.
4. **SOS Emergency** (available throughout Stage 4) — immediate stop, on-screen acknowledgement, manager alert/email, then follow-up.

### What CVI Actually Is, Mechanically (Supporting AR-WB-11) — adopted 27 Aug 2026

Before any cutoff number can mean anything, "CVI" has to be defined as an actual computed value, not just something the Auditor reads off a screen. Every source document up to this pass treated it that way — displayed, adjustable, submitted — without ever saying what produces it or on what scale. Jana flagged this directly: don't invent cutoffs before defining what's being cut. This section is the answer, worked out from the project's own architecture documents rather than assumed.

**CVI is a computed, case-level output of the rules engine — not a raw single number straight from the vision model.** Per the IBM x RMIT capstone brief's own architecture description: the pipeline "ingests video, samples frames, and classifies harmful content (violence, weapons, threat signals) using vision AI, then runs a configurable rules engine to produce a severity score, an incident timeline and a narrative summary." The brief's own IBM-component table is explicit about the division of labour: watsonx.ai's multimodal Granite/Llama models produce "frame-level vision analysis, entity tracking, severity signals" — i.e., per-frame classification tags plus a confidence/intensity signal per detected category — and a separate rules engine (built by the team, not IBM) aggregates those per-frame signals into the single case-level severity score the rest of this document calls the CVI. This also matches Naresh's own term for it in the client Q&A: "CVI (severity/violence index)" — an index, i.e. a derived/aggregated figure, not a raw model logit. So: **vision AI produces the raw per-frame signals; the team's own rules engine turns those into the CVI** — a composite, not something IBM's models hand over ready-made.

**Where this sits in the build timeline.** Per the brief's own phase plan, this is exactly why the real numeric schema doesn't exist yet: Phase 2 (Weeks 3–5) is "frame extraction and vision classification; structured-JSON output per frame" — the raw per-frame signals this section describes — and Phase 3 (Weeks 6–8) is "rules engine → severity score, incident timeline and summary." The CVI, the incident timeline, and the tag taxonomy are all downstream of work that hasn't been built yet. That's not a reason to leave the business logic undefined in the meantime — per the ordering already agreed in this document (BA defines the business structure first, Dev implements it against the real schema once it exists) — but it is the honest reason no one can currently point to a real, running CVI value and say "here's what 62 actually looks like."

**Scale — genuinely undefined upstream; 0–100 approved as the working placeholder scale, 27 Aug 2026 (team yes).** No source document (this note, the requirements doc, ARCHITECTURE.md, or the capstone brief) specifies whether CVI is a 0–1 probability-style figure, a 0–100 index, or something else. This note adopts **0–100 as the working placeholder scale** for the business-severity table below — chosen because it's the more legible, more nameable convention for a plain-language cutoff table a non-technical teammate needs to read at a glance, not because there's any technical reason to prefer it over 0–1. **This is explicitly a team-defined placeholder, not a technical spec, and the team has signed off on planning around it.** If Dev's actual rules engine (Phase 3) natively outputs a different scale (0–1 is equally plausible for a rules-engine confidence composite), the cutoffs below translate proportionally without re-deriving the underlying logic (e.g. "65 and above" becomes "0.65 and above") — only the units change, not the reasoning.

**How the rules engine likely turns many per-frame signals into one case-level number is itself an open design question — resolved below, not assumed.** A video isn't one frame; the rules engine has to combine signals across every sampled frame into a single CVI. The two obvious approaches are averaging across frames, or taking the worst single moment. This question turns out to be the same question as the "whole-video overall severity" gap raised separately in this pass — see the dedicated subsection immediately after the four-tier table below, which resolves it and feeds the answer back into this CVI definition.

### Four-Tier Business Severity Model & Cooldown Duration (AR-WB-11 / AR-WB-12) — Supporting Stages 6 and 9

The exact severity trigger and cooldown duration were previously fully open — no client ruling and no proposal existed anywhere. The team has since adopted a sourced model as its working design intention; it is not yet client-confirmed, but it is no longer an unresolved question for the team. The tier definitions and cooldown durations were already adopted in an earlier pass; **the CVI-range cutoffs are new in this pass**, added now that the CVI mechanism above gives them something real to cut.

| Level | Exposure severity | Examples | CVI range (0–100 placeholder scale) | Cooldown |
|---|---|---|---|---|
| S1 – Low | Disturbing but limited impact | Verbal aggression, non-graphic conflict, staged/synthetic violence with no visible injury | 0–39 | None — normal review |
| S2 – Moderate | Realistic or sustained distress | Real physical conflict, visible minor injury, aggressive audio, repeated distressing content | 40–64 | 5 minutes, after sustained/repeated exposure (defined below) |
| S3 – High | Graphic or psychologically intense | Serious injury, significant blood, death aftermath, realistic self-harm, sexual violence themes | 65–84 | 15 minutes, mandatory |
| S4 – Critical | Extremely traumatic / specialist material | The most severe content categories the platform handles | 85–100, **or forced regardless of score** if a floor-triggering content tag is present (tag list still open — see below) | 30 minutes minimum, plus a mandatory manager/support check-in and the option to stop or reassign the remaining shift |

**The CVI-range cutoffs above (0–39 / 40–64 / 65–84 / 85–100) are approved, 27 Aug 2026 (team yes) — a team-defined operational rule, not an external standard.** No external source produces these specific numbers, and none honestly could, since CVI is this project's own invented index, not a standard with published bands. What *is* sourced is the shape of the banding, not the numbers themselves: both the Australian Classification Board's official impact framework and the eSafety Commissioner's own industry guidance independently describe severity/impact as increasing with realism, detail, duration and repetition, and both apply their strictest classification band narrowly, to a small top tier, while the least-severe band covers the widest range of everyday content. The Classification Board's own six-point impact hierarchy (Very mild → Mild → Moderate → Strong → High → Very high, mapping to G/PG/M/MA15+/R18+/RC) works the same way: RC — the tier this platform's S4 content categories most resemble — is deliberately the narrowest, most tightly reserved band, not an even fifth of the range. The cutoffs above follow that same shape (a wide S1 band, a narrow S4 band) by analogy, not by any formula converting a real classification scale into a CVI number — because no such formula exists. **What would tighten this later:** once Dev's rules engine is actually built and run against the project's own synthetic/staged validation footage (Phase 3, and the accuracy validation the client explicitly asked for in the Q&A — a ground-truth accuracy graph over a sample case set), the team should re-calibrate these bands against real observed CVI distributions rather than keep the initial estimate indefinitely. This table is deliberately usable now, not a placeholder for "coming back to it later with no plan" — but it should be revisited once real numbers exist to check against.

**"Worst-moment-wins" for computing the case-level CVI from many per-frame signals is adopted here — see the dedicated subsection below for the full reasoning, which is shared with the separate whole-video-severity gap.**

**S4 does not trigger SOS, and this table's cooldown behaviour must not be read as if it did.** SOS (Stage 4's emergency action) is reserved exclusively for *unexpected* exposure — the AI under-tagged something and the Auditor was hit with worse content than the warning gate and severity tag led them to expect. Reaching S4 through a correctly-tagged case is a different situation entirely: the Auditor knew going in (via the warning gate and queue severity tag) that this was severe content, so nothing about it is unexpected. That's why S4's response, above, is the calmer mandatory manager/support check-in — not SOS — kept deliberately separate so a correctly-tagged severe case doesn't get treated as the same kind of emergency as an AI mis-tag. If an S4 case *also* turns out to be more extreme than its tags indicated, that's an unexpected-exposure event in its own right and SOS remains available throughout, exactly as it is for any other case — the two mechanisms aren't mutually exclusive, they're just triggered by different things (expected severity vs. unexpected surprise), not by the same S-level threshold.

**The content-warning pop-up (Stage 3) is not level-gated.** It appears before any potentially harmful content is shown, for any case carrying a content-warning flag at all — regardless of what S-level that case is later computed to be. This has to be true structurally, not just by convention: S1–S4 is computed from the CVI and tags at Stage 2 (queue view), after AI processing completes but before the Auditor has opened the case — the warning gate at Stage 3 is a separate, universal step that every flagged case passes through, not a condition that only some S-levels trigger. An S1 case still gets the same warning gate as an S4 case; the only thing that varies by level is what happens *after* review (cooldown, manager check-in), never whether the pre-viewing warning itself appears.

**Baseline mechanism — scope-corrected 27 Aug 2026 per Hyuna (PM) feedback.** S1–S4 is mapped using simple rule-based logic over two existing AI outputs: the AI's own generated CVI score range and the AI's existing content tags/flag reasons (already shown at Stage 3) — not a separate manual classification step, and not a bespoke multi-factor scoring model. This correction exists because Naresh's confirmed AI scope is integrating existing AI services (per the kickoff demo, the vision/content analysis runs on watsonx.ai's Granite or Llama Maverick models) rather than building or fine-tuning custom models — and the project's own IBM x RMIT capstone brief describes exactly this split of labour: vision AI classifies the content, then a *"configurable rules engine"* (not a custom-trained model) turns that into a severity score. Computing S1–S4 from a six-weighted-factor formula, however well-sourced the factor list, would mean building that custom scoring logic ourselves — outside the confirmed scope. This is a mechanism correction, not a tier correction: the S1–S4 levels and cooldown durations above are untouched, it's the *how*, not the *what*. A minimum-severity floor still applies and still makes sense under this mechanism: specific tags already associated with the platform's most severe content categories can force a minimum S-level regardless of the CVI score or clip length — the floor is driven by tag presence, not by the (now-demoted) six-factor calculation, so it survives the correction unchanged.

**S1–S4 sits alongside the AI's existing severity/CVI rating, not in place of it.** The CVI score originates as the AI pipeline's own computed output — see "What CVI Actually Is, Mechanically" above — and becomes the case's working assessment once the Auditor reviews it and, if needed, adjusts it before submission; both the original AI value and the Auditor-adjusted value are stored with the case (AR-AI-08 / CV-05). S1–S4 answers a different question — whether and how long a wellbeing cooldown applies. Keeping the two separate avoids overloading one score with two jobs and leaves the confirmed CVI mechanism untouched. The CVI range feeding the S1–S4 mapping above is specifically the AI's own auto-generated score at Stage 2 (queue view, where the severity tag has to already exist) — not the auditor's own adjusted CVI, which isn't submitted until Stage 5 and is too late to drive an S1–S4 tag the auditor needs to see before opening the case.

**"Sustained or repeated" for S2 is defined as:** continuous active exposure to S2-tagged content beyond roughly 2 minutes within a single case ("sustained"), or two or more S2-tagged cases reviewed within a single ~45–50 minute review block ("repeated") — that block length reuses the same micro-break window cited below rather than introducing a separate invented figure.

After an S3 or S4 case, the next case assigned should not itself be graphic. This is scoped deliberately narrow: a one-time filter excluding S3/S4-tagged cases from the single next assignment right after a cooldown, not a broader rule about spacing severe cases across a whole shift.

**Whole-shift severe-case spacing — closed, 27 Aug 2026 (Jana's call).** The broader version of this question — should there be an additional rule spacing severe cases apart across a whole shift, beyond the one-time post-cooldown filter above? — is now closed, not left open. Jana's decision: no additional whole-shift spacing rule for Sprint 2. The existing hard rule immediately above (next case after an S3/S4 cooldown can't itself be S3/S4) plus the soft rule below (30-minute recent-severity deprioritisation, Severity-Aware Assignment Layer 1) are the baseline. A broader shift-level spacing mechanism would risk duplicating what these two already do without solid evidence it's actually needed on top of them — so it's noted here explicitly as a **possible future enhancement**, not a current gap: if Sprint 2 role-play testing or real usage patterns later show auditors still getting an unusually clustered run of severe cases despite both existing rules, that would be the evidence to revisit this with.

### Whole-Video Overall Severity — Worst Moment vs. Weighted (Supporting AR-WB-11 / AR-WB-12) — adopted 27 Aug 2026

**The gap.** A video isn't uniformly severe throughout — a mostly mild clip with one brief graphic spike needs a rule for what the *whole case's* CVI/S-level should be. Dev's working default has been worst-moment-wins: the single most severe moment in the video sets the whole case's severity, even if everything else in the clip is mild. Before assuming this needs replacing with something more sophisticated (an average, or a duration-weighted score), it's worth checking whether real content-classification practice actually supports it — because if it does, "worst moment wins" is the defensible, citable approach, not a lazy default that happened to be first.

**It does — this is genuinely how the Australian Classification Board operates, not an invented analogy.** Per the Classification Board's own official guidance on how a rating is decided: "consumer advice gives information about the content... it usually describes the classifiable elements with the greatest impact" — a film's overall rating is driven by its most impactful content, not diluted by an otherwise mild runtime. A two-hour film with one scene of strong violence and nothing else remotely intense doesn't get an averaged-down rating because the other 118 minutes were mild — the strong scene sets the floor for the whole classification. This is a real, checkable, on-point precedent for worst-moment-wins as *the* established practice in the exact domain (screen-content classification) this platform's severity model already draws from for everything else in this table.

**One real refinement, not a replacement.** The Classification Board's impact test isn't a pure single-instant rule either — impact "depends on the frequency, intensity and the overall effect of the content," and the eSafety Commissioner's own guidance separately lists "repeated frequently" alongside "detailed" and "prolonged" as things that independently raise impact. So repetition of a serious element can itself matter, even without any single frame being worse than before. **This project already has a mechanism that captures exactly that nuance — it just wasn't stated as the whole-video aggregation rule until now:** the existing S2 "sustained or repeated" definition above (continuous exposure past ~2 minutes in one case, or 2+ S2-tagged cases in a review block) already treats repetition as its own escalation path, separate from single-moment intensity.

**Adopted rule:** the case's overall S-level equals the **highest S-tier reached by any single flagged incident in the video** (worst-tier-wins, not an average across runtime), **with the existing repetition-based escalation logic (S2 "sustained/repeated") layered on top** — so a video with several moderate moments can still escalate past what any single moment alone would trigger, without needing a new weighted-average formula invented from scratch. This means Dev's current default doesn't need replacing, just confirming and stating explicitly as the documented rule, since it turns out to be the genuinely defensible approach rather than an accidental placeholder. **This directly answers the open question in the CVI-mechanism section above:** the rules engine aggregates many per-frame severity signals into one case-level CVI the same way — by the maximum signal observed, not an average — consistent end to end from frame-level detection through to case-level S-tier.

**Reference:** `classification.gov.au/classification-ratings/how-rating-decided` (impact test: frequency + intensity + overall effect; consumer advice describes the elements of greatest impact) and eSafety Commissioner's Phase 1 Industry Codes Regulatory Guidance (Nov 2024), footnote 10 (repetition and duration as independent impact factors). **Approved, 27 Aug 2026 (team yes)** — worst-tier-wins, with S2 repetition-escalation layered on top, is now the documented, official whole-video severity rule, not just Dev's accidental default.

### Post-Submission Severity Reconciliation (Supporting Stage 5 / AR-WB-11, AR-AI-07) — new gap, found and proposed 27 Aug 2026

**The gap.** "Content more severe than AI indicated" already exists as a named decline reason (Decline & queue-skip reason list above) — the platform already anticipates the AI under-tagging a case the Auditor never even opens. But the mirror case is never addressed: an Auditor *completes* a case at Stage 5 and adjusts the CVI upward, past the AI's original S-tier, into S3/S4 territory the AI itself never flagged. Nothing currently says whether that triggers any of the protections a case tagged that severely from the start would have received — cooldown, mandatory manager/support check-in — or whether the adjusted rating is simply recorded as data with no behavioural consequence.

**Why this matters, not just as a completeness exercise.** This is functionally the same risk profile as an AI mis-tag or a mid-review AI/STT failure — both already treated as unexpected-exposure events (AR-AI-11) precisely because the Auditor ended up exposed to something more severe than they were prepared for. An Auditor who adjusts a case's CVI upward after review has, by definition, just experienced exactly that: content more severe than the AI's tag prepared them for, discovered mid-task rather than pre-screened. Leaving this case unhandled means the platform's wellbeing protections quietly stop applying exactly when the content turns out worse than expected — the one scenario CV-04 (wellbeing always wins, no exceptions) most needs to cover.

**Proposed rule — reuses an existing pattern rather than inventing a new one.** If the Auditor's adjusted CVI at submission (Stage 5) crosses into an S-tier at or above S3 that the AI's original score didn't reach, treat it the same way AR-AI-11 already treats a mid-review AI/STT failure: apply the cooldown and (for S4) mandatory manager/support check-in that tier would normally trigger, applied retroactively at submission rather than pre-screened at Stage 2 — since by definition it couldn't have been known before the Auditor reviewed the case. This costs nothing new to design: it's the same S-tier-to-cooldown mapping already adopted (AR-WB-11/AR-WB-12), just triggered from the Auditor's adjusted score instead of the AI's original one, in the one specific case where they diverge upward.

**What this deliberately doesn't do:** it doesn't apply retroactive protections when the Auditor adjusts *downward* (AI over-tagged, e.g. Naresh's own "football brawl" example) — a downward adjustment means the Auditor was actually less exposed than expected, which isn't a wellbeing gap needing a fix. It also doesn't change anything about pre-screen assignment weighting (AR-AS-05) or the queue-level severity tag, both of which correctly still use the AI's original score, since neither can know about an adjustment that hasn't happened yet.

**Status: proposed, needs your sign-off.** This is a genuine gap surfaced by end-to-end review, not a client ruling or an earlier open item — the underlying mechanism it reuses (AR-AI-11's unexpected-exposure treatment, AR-WB-11/12's tier-to-cooldown mapping) is already adopted, so adopting this closes the gap without introducing new unsourced numbers.

### Incident-Timeline "Flagged Incident" Cutoff (Supporting Stage 4 / AR-AI-03, AR-AI-04) — revised 27 Aug 2026 per Jana

**The gap.** AR-AI-03 says the system shows an incident timeline with timestamps; nothing anywhere defines what makes a moment count as a distinct, marked "incident" versus just part of the AI's general output. This is a policy call, not a technical one — it directly shapes what an Auditor sees flagged as "look here" before they've watched anything.

**Original proposal (superseded) and why it was overturned.** The first pass here proposed a minimum-duration gate (~2 continuous seconds) before a moment earned its own marker on the timeline, reasoning that a fleeting one-frame detection is closer to "incidental, not direct" than to something worth visually interrupting an Auditor's prep view. **Jana's call overturns this: no minimum duration should apply — a minimum shouldn't matter.** The reasoning holds up once weighed against this project's own standing priorities: the timeline's entire purpose is to prepare the Auditor for what's coming so nothing lands as a surprise, and this platform already treats *any* unexpected severity as the worst failure mode it can have — that's exactly why SOS exists, why AR-WB-07 logs and protects against unexpected exposure, and why CV-04 rules wellbeing outranks everything else, no exceptions. A minimum-duration gate is a legibility optimisation (fewer blips on the timeline) that trades directly against that priority: it would mean the one genuinely brief but severe moment — the exact kind of thing that causes real unexpected exposure — is the one thing most likely to get filtered out of the very tool meant to warn the Auditor about it. That's the wrong thing to optimise for on this platform. It's also consistent with a pattern already adopted elsewhere in this doc: the exposure clock counts blurred/muted/replayed viewing in full rather than discounting it for being "less real" exposure (Exposure Clock section above) — this platform consistently treats *any* real exposure as exposure, not just the version that's convenient to count.

**Adopted rule: every AI-flagged moment is marked on the incident timeline, with no minimum-duration threshold.** Whatever granularity the vision AI's own per-frame output ends up being (Phase 2, Weeks 3–5) is the granularity the timeline marks at — a single flagged frame gets its own marker, the same as a ten-second flagged sequence. This is simpler to build than the duration-gated version (no dwell-time tracking logic needed) and avoids inventing a number that had no real source in the first place — the ~2-second figure was already flagged as an unsourced team estimate, so removing it also means one fewer invented number in this document, not just a safer default.

**What this doesn't change:** every flagged moment already fed the tags/AI-summary panel and the overall CVI computation regardless of duration — that part of the original proposal was never in question. The only thing that changes is that the *visible timeline marker* now matches that same standard instead of applying a stricter, separate bar.

**Status: closed, 27 Aug 2026 (Jana).** No open figure remains here — there's no minimum to calibrate later, so nothing is pending on Dev's frame-sampling rate for this specific decision (Phase 2 will still determine the underlying detection granularity itself, but that's a technical implementation detail, not a business threshold BA needs to revisit).

Same sourcing as the Four-Tier Business Severity Model above. ### Severity-Aware Assignment & Manual Skip (Supporting Stages 1–3)

The consecutive-severe-cases risk raised alongside the severity model above is addressed as three layers, each covering a different part of the same problem, not one fix:

1. **Assignment-side, soft preference (Stage 1) — design closed, 27 Aug 2026 (Jana's call).** The existing weighted round-robin (exposure level + case count) gains one more factor: an auditor who was recently assigned an S3/S4 case carries a short-lived "recent severity" flag, and the assignment logic prefers an unflagged auditor for the next S3/S4 case, even if it would otherwise be the flagged auditor's turn. This is a preference, not a hard block — if every available auditor is flagged (e.g. a queue surge), the system falls back to normal round-robin so cases don't sit unassigned. This is a small addition to the existing weighting logic, not a rebuild. **The design itself is final** — Jana confirmed the business rule as described (30-minute deprioritisation flag, weighted-round-robin fallback when everyone's flagged). The only thing left is Dev confirming the whole mechanism is buildable as described against the real assignment logic — a feasibility check, not an open design question.
2. **Post-cooldown, hard rule (Stage 6/9, Four-Tier Business Severity Model above).** Already decided: the single case assigned immediately after an S3/S4 cooldown can't itself be S3/S4. Guaranteed, not just preferred, since this is the one moment the risk is both highest and known for certain.
3. **Auditor-side, manual skip (Stages 2–3).** The existing Decline mechanism (Stage 3) currently only triggers after opening a case and reaching the warning gate. It's extended here to also be triggerable directly from the queue view (Stage 2), using the severity tag already shown there, before opening — same non-judgment framing, same manager routing as the existing decline path (Research Note 1), just a second, earlier entry point rather than a separate mechanism to learn. This is the backstop for whatever the first two layers don't catch.

None of the three layers alone is sufficient — Layer 1 reduces how often this happens system-wide, Layer 2 guarantees the one highest-risk moment, Layer 3 gives the auditor a direct out for anything that still gets through. **Recency window — adopted 27 Aug 2026:** Layer 1's "recent severity" flag uses a **30-minute** window, per Dev's own suggested figure. An Auditor recently assigned an S3/S4 case is deprioritised — not excluded — from another S3/S4 assignment for 30 minutes from that assignment, while another eligible Auditor is available; if every available Auditor currently falls within their own 30-minute window, the system falls back to standard weighted round-robin (AR-AS-02) rather than leaving a case unassigned, consistent with this being a soft preference throughout.

**Decline & queue-skip reason list — adopted 27 Aug 2026.** Both Layer 3 above and Stage 3's warning-gate decline share the same reason categories, in order: **Content more severe than AI indicated** (surfaced first — the most operationally useful signal for spotting AI mis-tagging patterns, and the least emotionally loaded to click), **Near my exposure limit** (plain-language relabel of the earlier "Exposure Buffer" draft), **Personal Trigger**, and **Other** (with free-text comment). The queue-level skip (Layer 3) carries its own distinct reason value — "skipped based on visible severity, not opened" — so pattern-review can tell the two entry points apart later. None of the four options is pre-selected by default: research on default-selection bias finds roughly 60% of users read a pre-set option as the implicit "recommended" choice even when it's never labelled that way, so a pre-filled reason on a decline form would quietly steer auditors toward a reason that isn't necessarily theirs — exactly the kind of soft nudge Marielle Lee's own dark-pattern gut-check ("does the user have real freedom to choose?", Q7) is meant to catch.

### AI/STT Failure Handling (Supporting Stage 4)

Not previously described anywhere in this note or any other source document — adopted 27 Aug 2026, using design authority the client explicitly delegated (Naresh declined to specify fallback behaviour directly at the sprint review: "team should treat this as open/self-defined requirement").

If AI or Speech-to-Text processing fails or can't complete for a case: visual exposure defaults to **maximum blur**, not whatever the AI would otherwise have suggested — unknown severity maps to the most protective state, not a neutral one. The AI-summary panel is replaced with a distinct failure state, not a small badge easily missed — e.g. "AI analysis could not be completed for this video — severity score and incident timeline are unavailable. Review with extra caution." Before any raw content is shown, the auditor makes a deliberate choice — proceed with reduced AI support, or decline — rather than being silently routed into a degraded review.

If processing fails **mid-review**, after the auditor has already started (not caught at pre-screen): this is treated the same as an unexpected-exposure event — logged, wellbeing protections applied, manager notified — since a mid-review AI/STT failure carries the same risk profile as an AI mis-tag: the auditor may be looking at content with no severity information to prepare them.

### Exposure Clock — What Counts (Supporting Stage 4)

The counting rule referenced in Stage 4 above is adopted 27 Aug 2026, backed by real evidence rather than an internal guess: **active source-video playback counts toward the daily exposure total regardless of blur/grayscale/mute state; paused video and AI-summary-only viewing do not count; replaying a clip counts again, not once.** A 2026 experimental study found blur and grayscale did not significantly reduce immediate anxiety, negative affect, or intrusive-image effects compared with unmodified content — so counting blurred/muted time as real exposure is measuring the right thing, not being overly cautious for its own sake; the controls remain valuable for reviewer autonomy, they just shouldn't be assumed to reduce exposure risk. Replays counting again follows the same logic: re-exposure is still exposure, even if it feels repetitive to the auditor in the moment.

### Blur Intensity Control (Supporting Stage 4)

Adopted 27 Aug 2026, replacing "how many named levels (Low/Medium/High), and what do we call them?" with a different answer entirely: **don't use named preset levels at all.** Das, Dang & Lease (2020), *"Fast, Accurate, and Healthier: Interactive Blurring Helps Moderators Reduce Exposure to Harmful Content"* (AAAI HCOMP-20) — a peer-reviewed study run on real content moderators, not a general workplace-safety source — found that fixed/preset blur levels *reduced moderation accuracy* as the blur got stronger, while an interactive, moderator-controlled blur matched normal accuracy and significantly improved positive affect and reduced emotional exhaustion compared to no blur at all.

Adopted design: the blur toggle becomes a single slider, 0–100%, in small fixed step increments (not smooth/infinite, not three big jumps), defaulting to 100% (maximum blur) when a case opens. A live number next to the handle shows the current percentage. A marker on the slider track shows the AI's suggested severity level as a reference point, not a hard limit — the same "AI suggests, auditor decides" logic already used for the CVI rating stays consistent here. This also happens to match a component IBM's own Carbon Design System already ships (label + numeric readout + step increments), the design system this prototype is meant to align with per the 21 Aug 2026 Support Session decision.

Stage 4's SOS/wellbeing-check-in interactions and Stages 6–9's cooldown experience are genuinely open design space; each team-designed addition above is traceable to a specific research note or Marielle Lee recommendation (cited inline), not invented from scratch — treat this table as the team's working design intention for the two upcoming screens plus the cooldown addition, not something awaiting outside confirmation. Stages 6 and 9's trigger threshold and duration are a different kind of open, though: no client ruling exists for either — the Four-Tier Business Severity Model above is now the team's settled working design, not a confirmation from Naresh or Emily. Assignment weighting's consecutive-severity risk (Stage 1) now has a fully adopted design too, closed on the design side per Jana's 27 Aug 2026 decision — see Severity-Aware Assignment & Manual Skip above, including the 30-minute recency window; only Dev's feasibility confirmation remains. Whole-shift severe-case spacing is also closed (Jana's call, 27 Aug 2026): no additional rule beyond the existing hard post-cooldown filter and the 30-minute soft deprioritisation — see the note under the Four-Tier Business Severity Model above.

### False-Negative vs. False-Positive AI Error Prioritization (Supporting AR-AI-01 / AR-WB-11 / MR-OV-08) — adopted 27 Aug 2026, written down formally per Hyuna's question

**The gap.** Hyuna asked, informally, whether the platform should prioritise catching false negatives (the AI misses something genuinely harmful) or false positives (the AI over-flags something benign) when the two trade off against each other. An answer existed only as an unwritten chat reasoning — never given its own ID or citation, never checked against real evidence. This closes that gap properly rather than leaving a good answer undocumented.

**The original chat reasoning, restated:** prioritise false-negative mitigation, as a direct extension of CV-04 ("wellbeing always wins, no exceptions") — a false negative means an Auditor gets hit with harmful content the system told them wasn't there, which is exactly the unexpected-exposure failure mode AR-WB-07 and AR-WB-16 already treat as the worst thing this platform can do to a reviewer. A false positive, by contrast, costs an Auditor a few extra minutes reviewing something that turns out to be benign (Naresh's own "football brawl" example) — a workload/efficiency cost, not a wellbeing one, and one the human-in-the-loop override (AR-AI-07, CV-05) already exists specifically to catch and correct.

**Verified, not just re-asserted — this is standard practice in the actual domain, not just internally consistent logic.** Real trust & safety industry practice independently reaches the same conclusion for the same reason. GetStream's published moderation-metrics guidance states plainly that "low recall is a direct safety risk, especially in categories like hate, child safety, or self-harm," and that high-severity categories often carry a stricter, separate recall target from lower-severity ones — a close match for this platform's S3/S4, CSAM-adjacent categories specifically. The Trust & Safety Professional Association's own content-moderation QA curriculum treats precision and recall as distinct, category-weighted targets rather than one blended number, consistent with weighting recall (catching real harm) over precision (avoiding over-flagging) for the platform's highest-severity categories. Separately, peer-reviewed work on operationalising content-moderation "accuracy" (Wei, Zufall & Jia, AIES 2024 — see the MR-OV-09 callout in the Manager Assumptions Note for the full citation) confirms that raw blended accuracy is the wrong metric to report at all for an imbalanced classification task like this one, reinforcing why recall/precision need to be tracked separately rather than folded into one number. That's the same asymmetry this platform's own CV-04/CV-05 reasoning already lands on, from independent sources. Recall (the rate of true harmful content actually caught) is the metric that corresponds to minimising false negatives; precision is the metric that corresponds to minimising false positives.

**One honest refinement:** prioritising recall doesn't mean false positives are costless — a rising false-positive rate still has a real Auditor workload/fatigue cost worth watching, even though CV-05's override design already absorbs it structurally. If Auditor decline/override patterns later show false positives clustering heavily, that's the signal to revisit the balance, not a reason to treat recall-priority as fixed forever.

**AR-AI-13 (proposed, not adopted this pass).** *Where the vision-classification pipeline or rules engine requires a threshold trade-off between precision and recall (i.e., between under-flagging and over-flagging), the system shall be tuned to favour recall — minimising false negatives — over precision, consistent with CV-04. This is a business-priority instruction for Dev's Phase 2/3 model- and rules-engine tuning, not something BA/UX can implement directly; it also sets the framing for MR-OV-08's validation view, which should report recall as the headline metric rather than a single blended accuracy figure — see the Manager Assumptions Note, Section 1d, for the full accuracy-threshold reasoning this connects to.*

**Status: DEFERRED, 27 Aug 2026 (Jana, BA scope decision).** The reasoning held up under verification, strengthened with real external citations rather than resting on internal logic alone — but formalising it as its own numbered requirement went beyond this task's actual scope (finalising persona requirements against the agreed client scope, not adding new proposals). Kept as reasoning on record; the underlying priority logic still lives implicitly under CV-04 regardless of whether it gets a separate written-up ID.

**Sourced from:** GetStream, "Moderation Metrics & KPIs: How to Measure Content Safety" (getstream.io) — industry guidance on recall as the safety-critical metric for high-severity categories; Trust & Safety Professional Association's content-moderation QA curriculum (tspa.org) — precision/recall as distinct, category-weighted targets in real T&S practice; and Wei, Zufall & Jia, "Operationalizing content moderation 'accuracy' in the Digital Services Act" (AIES 2024, arxiv.org/abs/2305.09601) — peer-reviewed confirmation that raw accuracy misleads under class imbalance. CV-04 and CV-05 (client-confirmed) supply the platform-specific priority ruling this recommendation extends.
